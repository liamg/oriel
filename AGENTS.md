# Oriel: instructions for agents

Oriel is a native, vim-first, AI-first IDE written in Go: half professional editor, half agent harness.

## Where things are

- `docs/architecture.md`: the module layout, the layering rules, the registry, plugins, sessions, the toolkit and
  how things are tested. Read it first.
- `docs/configuration.md`: settings files, precedence, the sample `init.lua` and every option (a test checks the list
  against the registry).
- `docs/api.md`: the `oriel.*` Lua API, generated by `tools/cmd/apigen`; `docs/examples/`: example plugins.
- `app/shell/help/pages/`: the in-app help.
- `testdata/mockups/`: the reference screens the fixture workspace is held to.

## Working on a change

1. Start from an issue. Read what it links, and look for what already exists that it can build on (widgets,
   registry and host helpers, `gitx`, test harnesses). Name the general pieces it needs that don't exist yet: they're
   built first, as their own units.
2. Write the acceptance tests first. They fail.
3. Implement until they pass on macOS and Linux.
4. If the change alters what `docs/` or the help pages describe, update them in the same change.

If the issue is silent or ambiguous on something that matters, ask rather than invent.

## Rules

- **Extensible by construction, never hacked in.** Every feature is built on the same public APIs a plugin would use
  (registry, events, hooks, views, decorations, commands, providers; `docs/architecture.md`). Concretely:
  - No special-case methods, flags or back doors for one feature. If a feature needs something the API can't
    express, **extend the API generally** (and its Lua/RPC bindings), then build the feature on it.
  - Built-ins are written as if they were plugins: replaceable, removable, and configurable from Lua.
  - A good test: could someone build this feature as a third-party plugin with the same result? If not, the API is incomplete. Fix that first.
  - New Lua API surface is annotated with `//oriel:api` in `script/api`, and `docs/api.md` regenerated, in the same
    change.
- **Reuse before you build, everywhere.** Search for an existing component, helper or harness before writing one.
  When the same thing would exist twice, extract it into the package that owns it and use it from both. Fix a
  behaviour where every user gets it (the toolkit, the shared package), never by patching one screen or caller.
  - **UI**: views are composed from `ui/widget` (`Clickable`, `Button`, `IconButton`, `Segmented`, `Tabs`, `List`,
    `Chip`…). No view repeats `c.Next` / `c.Interaction(...).Clicked` / `Interactive` / `Cursor` / `Role` to make
    something clickable (`TestViewsUseWidgetsForClicks` fails if one does). If no widget fits, add a general one to
    `ui/widget` with its theme tokens and a test, then use it.
  - **UI behaviour lives in the toolkit too** (`docs/architecture.md`, "Rendering and the toolkit"), so every screen
    gets it and none re-solves it:
    - A float's `Z` is a named layer (`ui.LayerPage`, `ui.LayerDialog`…), never a number; a float inside another
      inherits its layer (`TestFloatsUseLayers`).
    - A full-window page is `widget.Page`; a dialog over a scrim is `widget.Scrim` (an outside click closes it)
      with Escape. Any closable surface gets both an Escape path and a visible close (a tab's ✕, a button). Docked
      views close with Escape and their tab's ✕.
    - A key that never arrives may be the backend's: gio keeps Tab for its own focus moves unless the window's key
      filter names it (`render/gio/window.go`).
    - A widget hands keys it doesn't use up with `Ctx.PassKeys`, so Escape on a focused control reaches its page.
    - Keyboard focus has one owner, the toolkit: a view never grabs it in build. It marks its default target
      (`Style.DefaultFocus`, `InputOpts.DefaultFocus`), which focus takes when the view opens or an overlay over it
      closes, and moves it on purpose once with `Ctx.RequestFocus`; `Ctx.Focus` is the toolkit's own. Test a field
      by clicking into it and running frames with the others open and an overlay over it (`TestFocusStaysInAClickedField`).
    - A frame that reads input asks for the next; don't add a `WakeAt(now)` to show what a click changed.
    - Text fields edit with the platform's keys (`widget.Input`); a number field takes `Accept: widget.Digits`
      and shows `Invalid` while it's wrong.
    - Text never runs out of its box: a row too narrow cuts its text with "…", so don't measure or cut labels by
      hand. A strip of tabs that may not fit is a `widget.Strip` (it scrolls sideways with no bar, counts what's
      past each edge, and brings the active item into view only when it changes); a table
      scrolls sideways (`ScrollX`); a status chip that must stay whole is `Keep`.
  - **Code**: shared logic lives in the module that owns it (`gitx` for git, `registry` for contributions, `core`
    for state), not copied into each caller; tests share harnesses (`apptest.Scene`, `apptest.NewWindow`, `vimtest`) rather than
    growing new ones.
- **Test-first, with sources.** Behaviour tests cite a vendored spec with a verbatim quote, and vim expectations are
  checked against headless nvim (`make oracle`). Never write an expected value from memory, and never weaken
  a failing test to get to green.
- **Test the way it's used.** Drive a control through the toolkit (click it, press keys on it, with timeouts on and
  over other overlays), not by setting the state it would set; a test that turns off a timeout or opens one view
  alone misses the bugs people hit.
- **Names are plain words.** Public API (Lua, commands, options) says what it is: `oriel.option`, not `oriel.o`; a
  user who wants it short aliases it (`local o = oriel.option`).
- **Dependencies.** Stdlib, `golang.org/x/*` and `github.com/liamg/*` are free to use. Anything else must be approved
  and listed in `tools/depcheck/allowed.txt` first (`make depcheck` fails otherwise). Ask; don't add. Writing it
  ourselves is the default alternative. `vendor/` is committed and checked (`make vendor-check`); native and wasm
  parts are built from pinned sources, never downloaded prebuilt.
- **Claude is driven through its interactive CLI in a PTY with hooks, never `claude -p`** (that path is billed per
  token, while the interactive CLI uses the user's subscription). The plan's windows are read from the usage API
  Claude Code's own `/usage` reads (`api/oauth/usage`, with its sign-in's token: it asks no model, so it bills
  nothing); when that can't be used, from the hidden `/usage` read: an interactive `claude` with Oriel's mod, typed
  `/usage`, whose mod reports `$.session.usage()`. `claude -p "/usage"` gives no percentages. The windows are read as
  data, never off the screen; otherwise they come from live sessions.
- **Platforms.** macOS (primary) and Linux, from the start. No platform-specific code without the other platform's equivalent or a build tag.
- **Interfaces at seams.** Follow the module layout and layering in `docs/architecture.md`, which `tools/layout`
  enforces: `text`, `edit`, `vim`, `syntax`, `lsp`, `dap`, `core`, `agent` and `term` never reach `ui` or `render`.
- **Commits**: conventional style, one logical change each (`feat(vim): motions and operators`).
  **Never push**: the user pushes.

## Ratchets

- `tools/ratchet` counts what the code is moving away from: kind special cases, `*shell` outside `app/shell` (at 0),
  `cfg.Store`/`cfg.Host`, long functions and files in `app/` and `host/` (both at 0), `Focus` calls (at 0) and
  multi-line `widget.Input`s outside `ui/`. A count may only fall: never raise a ceiling; lower it when your change
  drops a count.
- `tools/layout` keeps `app/<feature>` packages apart: a feature never imports another, nor the root `app`; features
  share `app/kit` and meet through registry services, and their tests drive the app through `app/apptest`.
- `tools/layout` keeps the session host's parts (`host/agentrun`, `host/worktree`, `host/github`…) apart: each sees
  the host as a `host/hostcore` State, and never imports another; only the `host` facade wires them together.
- `cfg.Store` and `cfg.Host` are at 0: a plugin reads and changes the state through its `plugin.Host` (`State`,
  `Apply`), and reaches the session host and other features through registry services (`Editors`, `GitTrees`,
  `CodeSites`, `Ships`, `Sessions`, `host.Access`; `docs/architecture.md`, "Registry and services"), commands and hook events,
  never another plugin's fields.
- Kind special cases are at 0: code asks a session's kind (`registry.Can`, `Label`, `Chips`, kind-scoped
  contributions) rather than comparing `core.Kind*` or reading another kind's data. A kind's own files say so with a
  `//oriel:kind <kind>` line, and only they may name it (`docs/architecture.md`, "Sessions and kinds").
- `make leakcheck` refuses private names in tracked files; CI passes the names in the `ORIEL_LEAK_DENYLIST` secret.
- Package-level state is at 0 (`tools/ratchet/state.go`): a package-level var that's written after it's declared,
  or holds a lock, an atomic, a channel or a pointer to something made, is shared by every app and test in the
  process. Put it on the instance that owns it (the app, a plugin, the host, a client, a UI with `ui.Keep`) and
  release it on Close; the few safe ones (init-time registries, embedded tables) are listed with why.
- Tests write package-level vars only through `testhook.Set` (at 0), which puts them back; better, the knob is a
  Config or options field. Every harness calls `isolate.Test` first: a TMPDIR of the test's own, and a leak check
  that fails the test leaving goroutines running once its cleanups (its app, window and host closing) are done.

## Coding style

- No essay-style comments. Keep comments short and to the point; no 10-line comments before 3-line functions.
- No comments about history or fixed bugs; that's what git is for. Comments describe the code as it is now.
